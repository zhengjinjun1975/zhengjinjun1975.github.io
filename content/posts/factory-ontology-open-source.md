# 工厂本体 factory-ontology：本体问答工具开源，让中小企业台账学会说话

企业最值钱的资产，往往最说不清楚。数据躺在 MES、ERP、Excel 台账里，业务人员不会 SQL，老师傅凭经验拍脑袋，新人对着字段名猜含义。大模型能聊天，但把台账丢给它，它编起数字来理直气壮。这不是模型的错，是数据没有被划定边界。

factory-ontology 是一套开源的工厂本体问答工具。它用本体给数据划定语义边界，让机器在边界内确定性回答，边界外用混合检索兜底，目标人群是数据没被用起来的中小工厂。数据还是那份数据，但从台账变成了能对话、能溯源、能沉淀的资产。

## 有台账，不等于有数据资产

中小企业不缺数据。设备台账、生产批次、质检记录、原材料库存，每张表都是几年攒下的真金白银。缺的是把数据变成资产的那层转化。

数据资产不是存了多少 G，而是能不能被问、被复用、被沉淀。一家阀门厂有 8 张表、上千行数据，如果只能靠人翻 Excel，那它就是一堆孤立的 CSV。如果业务人员能问"功率最大的设备是哪个""有多少台球阀在待检修"，每一问都带证据，数据才算活了。

全球都在把数据资产化、登记化。企业的普遍困境是：有数据，但绝大多数没被利用起来。中小企业是缺口最大的一群。

## 本体：给数据划定语义边界

大模型不认识你的表。让它直接读 CSV，它不知道 device_name 是人话里的"设备名"，不知道 status 是状态，更不知道设备表和生产批次表怎么关联。

本体解决这件事。它把一张表是什么实体（设备/产品/原料/批次）、字段是什么属性（编号/数值/状态/类型）、表之间怎么关联（生产/消耗/交付），声明成一份机器能读的 schema。建好本体，业务人员问"报警的空压机有几台"，系统在 schema 划定的范围内确定性回答，不靠猜。

本体不是学术意义上的 W3C OWL 推理体系，而是一份轻量的 JSON schema。工业界普遍对 RDF/RDFS 做工程化封装，提供类继承、属性多态，而不是直接上重量级 OWL。轻，所以快。换一个工厂，换一份 schema 和词典，代码不动。

## 本体 + RAG 混合检索：为什么这是趋势

过去两年，企业级 RAG 的演进方向清晰：本体和知识图谱约束 RAG，减少幻觉，提升可解释性。

主流的 GraphRAG 用 LLM 从文本抽实体关系构建知识图谱，把"减少幻觉、全局多跳推理"当核心卖点。学术界更进一步，OG-RAG 把领域本体当锚点约束检索，实测准确事实召回 +55%、回答正确性 +40%、归因速度 +30%、基于事实的推理准确率 +27%。

这些数字指向一个共识：向量检索保召回，图检索保精度，两者互补而非替代。混合检索的融合算法 RRF（倒数排名融合）被验证稳定优于单一检索。单一靠向量 RAG 答得流畅但不可信，单一靠规则引擎覆盖不了开放问题，把本体约束、规则引擎、图检索、向量语义串成一条链，各管一段，才是正解。

## 本体建模：schema 驱动 + 模型辅助

本体建模是最容易被低估的环节。它决定了问答能覆盖多广、多准。

factory-ontology 用 schema 驱动建模：一份 ontology_schema.json 显式声明实体、关系、属性语义角色（哪个是编号、哪个是数值、哪个是分类），schema 约束 + 类型体系 + 跨表图遍历 + 标准 N-Triples 输出。没有手写 schema 时，suggest_schema 从数据自动推断实体、关系、约束。

模型在这个环节是辅助，不是主角。行业共识是：schema/本体定义是 LLM 构建可靠知识图谱的关键，用 schema 约束关系、类、属性保证一致性，LLM 负责出三元组。自动词典生成从表名和字段名推断实体概念，自动产出实体映射、数值字段、类型映射、同义词。换任何行业建库即生成查询映射，无需硬编码。模型辅助 + 人工校准，是现实最优解。

## 确定性优先，大模型兜底

这可能是整套设计里最关键的分层。规则能答的，绝不交给模型。

传统 RAG 有两大局限：向量相似度与知识推理之间有空隙，对数值、时序、专家规则不敏感。这正是"模型算错数、编数据"的根源。成熟的架构是置信度回退：规则高优先级保证合规稳定，LLM 置信度低时触发兜底。

factory-ontology 的检索降级链是：规则引擎（数量/极值/平均/过滤/范围，零 token、可复现）→ 逻辑推理桥（LLM 转逻辑查询后确定性执行）→ 本体引导 GraphRAG（沿关系路径扩证据）→ BM25+向量语义 RRF 融合 → LLM 兜底。规则覆盖结构化查询，图检索覆盖关系和多跳，混合检索覆盖语义模糊，LLM 只在最后兜底。且兜底也区分两类：数据缺失的极值查询，如实说"知识库没有这个数据"，不编数字；咨询建议类问题，给专业建议并声明无唯一答案。

代价明确：不写 SQL 换来的确定性，边界就是模板本身。

## 沉淀企业数据资产

问答只是入口，沉淀才是价值。

每个企业绑定一份独立本体，用所在行业的数据建模，一企业一行业一数据，多租户隔离。建好的本体、词典、schema 全部外置成配置，换领域只换配置。问答过程中的反馈会沉淀成资产版本，本体与词典随使用持续精进，形成"越用越懂这家工厂"的循环。

数据不出厂。核心路径纯标准库，本地模型可全离线运行，甲方数据永不上传。语义资产，沉淀在企业自己的环境里。

## 实证：18 个行业验证

理论要落到数字上。factory-ontology 已用 18 个行业合成数据集加 UCI AI4I 公开数据集做全行业验证（阀门/化工/机械加工/船舶/环保/食品/图书/能源电站/电力/汽车零部件/电子/家电/纺织/塑料/医疗器械/家具/五金/AI4I 预测性维护），换行业只换词典与 schema，规则引擎与检索链路代码不动。

UCI AI4I 预测性维护数据集 1 万行真实制造传感器数据，61 个评测问题，61/61 = 100% 命中。多领域 benchmark 100%。对照实验里，裸 LLM（不加本体、直接把数据喂给模型）同批问题命中 7/9 = 78%，差的恰好是计算类（平均值、总和）。

GraphRAG 开放式问题 8/8，同义词容错 8/8。问"不锈钢"，能命中 CF8/CF8M/304/1Cr18Ni9Ti 等牌号。pytest 29 项全绿，CI 自动运行。

## 开源独立，服务作补充

factory-ontology 的内核完全开源，Apache-2.0，可独立运行，不依赖任何闭源组件。核心路径零第三方依赖，一条命令启动，能带进任何现场。

闭源交付工具和 FDE（领域工程师）辅助套件，只是服务能力的补充，不是必备品。开源的算法内核自己就能完成"数据进，答案出"的完整链路。三者合起来是完整产品套件，但开源工具自己就能站稳。
